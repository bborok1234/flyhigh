# Flyhigh OpenCode Adapter

Generated by `scripts/generate-adapters`. Canonical behavior lives in Flyhigh skills and references.

## Operating Rules

- Use Flyhigh as a local-first engineering harness, not as a separate runtime.
- Keep changes scoped and evidence-backed.
- Use generated run artifacts for substantial work.
- Update project memory only with durable facts.

## Available Flyhigh Skills

- `flyhigh-analyze`: Use for read-only repository investigation, root-cause mapping, architecture discovery, or evidence-backed answers before planning or implementation.
- `flyhigh-implement`: Use for scoped code or document changes after enough context exists; preserve user changes, follow local patterns, and verify changed behavior.
- `flyhigh-learn`: Use after meaningful work to update local memory, capture recurring hazards, and propose eval-backed skill improvements.
- `flyhigh-plan`: Use when a task needs PRD, design, acceptance criteria, risk review, or test-shape planning before implementation.
- `flyhigh-project-bootstrap`: Use when starting Flyhigh in a repository or refreshing project instructions; inspect stack, commands, tests, conventions, hazards, and create or update AGENTS.md plus optional memory skeleton.
- `flyhigh-qa`: Use to validate claims with targeted tests, typechecks, builds, smoke checks, generated artifact inspection, or adversarial QA.
- `flyhigh-review`: Use for defect-focused code review of local changes, pull request diffs, design changes, or generated agent output.
- `flyhigh-session-handoff`: Use when ending, pausing, or compacting a session; summarize current state, decisions, files changed, validation, blockers, and next actions.
- `flyhigh-ship`: Use when preparing completed work for commit, pull request, release, or handoff with final validation and concise delivery notes.
